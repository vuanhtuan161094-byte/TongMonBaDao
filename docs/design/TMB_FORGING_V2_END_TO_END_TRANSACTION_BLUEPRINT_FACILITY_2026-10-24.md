## 3. One complete work-order state machine and transaction boundaries [PROPOSED]
| State | Entry guard and action | Save/replay invariant |
|---|---|---|
| `REQUESTED` | player/auto policy selects exact recipe, legal worker and facility/slot/realm. Dry-run validation only, no mutation | duplicate request token maps to same request |
| `QUEUED_RESERVED` | atomic registered-ID + stock + lock/reserve check, hold full bill under **same Sect Warehouse availability ledger**, persist order+hold+seed | not counted as consumed; 2 orders cannot hold same 10 units |
| `ACTIVE` | worker has this Luyện Khí job as ONE active job; facility slot occupied; advance work by canonical eligible sim ticks | no other simultaneous job for worker; snapshot legal work speed |
| `PAUSED` | no valid worker/unsafe Injury/facility unavailable → preserve remaining ticks + hold; explicit reassignment after revalidation | no free time progress nor extra output |
| `RESOLVING` | due work exactly once; calculate deterministic grade/lines from frozen seed/version; prepare result item and receipt | subsequent resolves use same frozen item ID and result |
| `COMMITTED` | **one atomic authority transaction**: remove held materials from canonical stock once, insert exactly one unique item with same item ID + credit authorized profession completion/XP once, mark receipt committed | no double deduction, no repeated item/XP when recovering from crash |
| `ACKED` | release order worker capacity, mark item available in Sect Warehouse; optionally queue auto-equip as separate legal transaction | UI status is observer, no additional material/item mutation |
| `CANCELED` | allowed while QUEUED_RESERVED → free exact hold; ACTIVE cancel vs pause/partial refund remains **OWNER OPEN**; don't invent post-work refunded inputs | repeated cancellation not a free resource faucet |

**Important reserve semantics:** current `WarehouseSystem.reserve_min` is a *global owner keep-minimum*, NOT a hold belonging to an individual Forge order. Proposed `order_holds` are persistent in the **same warehouse authority**, not the separate old `forge_materials`. For each resource r:
`available_to_new_order(r)=0 if owner_locked(r); else max(0,stored(r)-reserve_min(r)-sum(active_order_holds(r)))`.
Multiple lines of the same material in a bill are aggregated before checking. Material is still in canonical Warehouse while held; it is not double-debited as both hold and consumption.
**Choose one atomic end model [RECOMMENDED]**: hold on acceptance, debit on COMMITTED along with item insertion; release exactly its own hold in same atomic step. If robust atomic multi-object save is unavailable in current engine path, use a durable versioned journal with before/after images and replay keyed by receipt until both resource and item state reach committed state; half-written states must never be acknowledged as success. Never apply "debit on acceptance" AND again on COMMITTED.
**Alternative valid but not selected:** debit into tracked reserved material escrow at start and refund on queued cancel, with clear single owner; would need different journaling; do NOT MIX both models.
**Worker speed and production:** one assigned active Luyện Khí disciple with authorized work job; determine `Profession Speed =1+.01×level`, generic `work_speed` modifiers, optional recipe affinity if authored, facility factor if actual authority. Proposed work ticks `ceil(base_action_ticks / validated_total_work_speed)` (time unit canonical sim ticks). Snapshot once on active order start to avoid weapon-swap speed exploitation. Logistics/workplace travel is separate valid time or explicit deterministic overhead; work ticks don't advance while PAUSED/unassigned/injured. No double multiplication of output or technique/Tu Vi by work-speed. Profession XP granted once at completion based on authorized XP flow; XP increase itself cannot cause repeated grade roll on same order.
**Time controls:** 1×, accelerated and offline tick replay process due orders in deterministic order (`due_tick` then `order_id`); changing visible camera/closing UI doesn't advance work. One Active Job, full repair of Injury and auto reassignment must be respected; no surprise new 'forge stamina' wallet.
**Facility/queue:** one order occupies one actual craft lane and valid worker; number of lanes capped only by real building worker/crafting capacity, not imagined 4 forever. Queue priority manual / auto policy needs owner-approved precedence and starvation safeguard. AUTO should not craft while resources locked for medicine/breakthrough or while disciple has another job.
