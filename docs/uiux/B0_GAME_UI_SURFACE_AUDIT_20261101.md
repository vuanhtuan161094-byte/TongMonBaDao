## Cross-cutting findings

1. **Visual verification is the first blocker.** Static inspection cannot establish readable text, uncropped panels, finger targets, colors, density or real art scaling. The PR #64 screens explicitly remain uncompiled/unplayed.
2. **Image availability is uneven.** The RC package has three Source A static building-image candidates. Residence and Guidance exist on E: only; UI atlases/prefabs have not been mapped into the Godot visual registry. Candidate != approved.
3. **Text is doing much of the work.** P3.2 operations, Technique Archive, six-tab Hall, roster and PvE each encode important state in labels. Convert stable categories/status into visual chips; retain exact numbers and descriptive names for accessibility and truth.
4. **Touch layout must preserve actual actions.** A compact drawer should not hide the map/hotbar or place destructive/paid choices next to one-tap convenience controls. Current function bodies expose real transaction/selection actions; any redesign must bind those same commands.
5. **Large-sect scale:** use filters, role counts, grouped workers and search rather than drawing every disciple with a label. No claim about crowd FPS is made here.

## B0 priorities

- **P0, first:** obtain the normal Godot import/GUI evidence through Codex A's accepted QA path; capture the actual Hall, Residence, Guidance and a crowded combat scene at 1280×720; resolve Residence door coordinate evidence. B0 itself did not launch Godot.
- **P1:** create visual hierarchy and icon taxonomy for building status, cost, progress and receipts; measure existing text-heavy panel content; preserve state-backed actions.
- **P2:** theme polish, transitions and decorative accents after readability, touch interaction and canonical-action binding pass.

No finding in this audit authorizes a gameplay edit or asserts that a visual bug was observed on screen.
